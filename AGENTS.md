# Working on ububall

## Scope

- Ububall is a standalone 3v3 physics hockey game and collectible ubu ecosystem (incorporating Ubu Mint). Read README.md before planning or changing it. The deployment instance run on Cloudflare is saved to `ubumint-cloudflare`.
- The 1024-bit DNA schema, local .ubu signing, batch storage, Cloudflare application implementation and configurable per-account lifetime mint limit are permanent specifications. Read docs/dna.md, docs/ububall.md, docs/uburithm.md, docs/ubu-file.md and docs/worker.md before relevant work. Deployment, production keys, creating/configuring external accounts, trading, and encryption remain distinct operations requiring explicit configuration.
- Distinguish core architecture and game rules from proposed ideas or work-in-progress experiments. Do not turn an agent recommendation into an approved protocol decision.
- Production credentials, private keys, and mint secrets must never be embedded in client-facing or browser code.

## DNA and ubucodes

- DNA is random input to permanent deterministic generation rules, not merely a serialized list of resulting traits.
- DNA is exactly 1024 bits (128 bytes). Assigned field meanings are fixed; additions use only the unassigned reserve bits 598–1013. Old 256-bit beta and 512-bit ubus have no compatibility path. Preserve all 128 bytes when reading, storing or exporting. All thirty-two rare material patterns are implemented in the shared renderer with a 5-bit gate (1/32) and 5-bit selector. Preserve their fixed assignments and the default matte treatment for inactive gates.
- Approved layout: 64-bit name seed, five 18-bit attribute slots, 24-bit mouth rolls, 40-bit mouth geometry, 40-bit eye controls, 24-bit lid rolls, 40-bit lid geometry, 20-bit lid flips, 8-bit corner curvature, two six-bit central mouth rolls, 10-bit opening width, 2-bit notch curvature (visual traits: bits 0–373, 374 bits total), 15 core stats across Movement, Physical, Engagement, Super (bits 374–493, 120 bits total), 4 Super ability slots (bits 494–509, 16 bits total), AI tactical brain (bits 510–533, 24 bits total), Web Audio voice synthesizer and goal fanfare melody (bits 534–597, 64 bits total), 416 unassigned reserve bits (bits 598–1013), and final 10-bit Ubuquity (bits 1014–1023). Total = 1024 bits. docs/dna.md is authoritative.
- Eyes are solid filled discs with overlaid irises/pupils, not hollow rings. Iris radius equals the prototype opening radius (30.7126), with no seam-concealing oversize. Textures rotate about the ubu outer-circle center.
- The official naming algorithm is the uburithm (packed SplitMix64 generator), generating names for all DNA while retaining letter rules and structural odds. Its packed flags, quotient recycling and chunk draw order are fixed in docs/uburithm.md. Future efficiency changes must preserve the packed outputs.
- Approved input paths: exact text encoded as UTF-8 then double SHA-512 into complete 128-byte DNA (first 64 bytes SHA-512(text), second 64 bytes SHA-512(text + '\x01')); random DNA generated directly (128 bytes); imported DNA read directly without rehashing. Preserve text case, whitespace and leading zeros. Initialize the name stream directly from the first 64 DNA bits.
- MSB-first bit order, uburithm calculation, slot roles, geometry, curves and finishes are accepted. Default matte and thirty-two material IDs are assigned in docs/dna.md. The working .ubu profile is in docs/ubu-file.md; no encryption is selected.
- Keep DNA interpretation separate from its plain, signed or encrypted transport envelope and host acceptance policy. Never reinterpret failed protected codes as plain codes.
- Two .ubu forms are implemented in ubu-file.js: unsigned/custom DNA and an Ed25519-signed issuance certificate. Both use the 1024-bit DNA. Custom ubus never imply official issuance or registered ownership. Signed imports require a caller-trusted mint public key, with no unsigned fallback or file-supplied trust. Hosts may require signed files. The demo has no configured mint trust and imports/exports custom files only; never install test keys as production trust.
- The mint must generate random DNA itself for ordinary minting. Do not authorize caller-selected seeds through the normal mint endpoint.
- Mint-signed certificates include a permanent twelve-digit serial (000000000001–999999999999) covered by the signature. The registry allocates serials atomically, uniquely per mint, without reuse or wraparound; retries must not mint twice. Custom files have no official serial. This metadata does not alter DNA.
- Approved batch policy: default 1,000, configurable for subsequent batches. Prepare private random DNA/IDs/serials, distribute uniformly without replacement, sign on authorized allocation and start the next batch after exhaustion. Serial order is creation order. mint.js supplies atomic/idempotent allocation; mint-local.js is the Node SQLite adapter. worker.mjs supplies Durable Object storage and alarm scheduling, Discord OAuth and a configurable lifetime allowance (default 0). Enforce allowances in the allocation transaction. Never expose the internal service without authentication; see docs/mint.md and docs/worker.md.
- Starter packs are an exception to batch distribution: one signup pack per account and one daily pack per UTC day, three ubus from the three rarest rarity deciles, drawn outside batches and outside the lifetime limit. Missed days do not carry over, and the daily pack comes before regular packs. There are no practice ubus: guests and CPUs get three ubus from the same deciles, and guests cannot keep theirs. See docs/mint.md.
- Ed25519 and exact signing bytes are implemented; production trust distribution, key rotation and mint allowances remain design work. A public verification key must not grant minting authority. Test private keys remain ephemeral and must never be committed or configured as official mint keys.

## This is a game: custom UI only

- Design requirement: ububall is a game, played inside Discord Activities and mobile browsers, not a typical web application. Every menu, dialog, dropdown, picker and confirmation must be custom-built and game-styled.
- In Discord, sign in to the same-Activity lobby as Not ready. Show avatar/name/status cards four per row and a dominant Ready to play action beside the rink. Allow challenges to Ready and Not ready users; challenges open rules/team setup. Automatic matchmaking starts immediately, with Change rules available before the first launch. Keep CPU play and other modes secondary. The Activity shares the site's Ubu Mint and Collection tabs.
- Deliberate Activity departures fully dispose connections and forfeit active matches; network interruptions keep reconnect grace. Discord participant membership is authoritative. Show loading spinners and actual errors, without routine status/instruction copy. Opponents share one two-column card with VS between avatars. Clicking an active match watches it; same-Activity spectating defaults on and either player may disable it in the pause menu. External watch links require explicit sharing.
- Keep a fixed spinner slot immediately after the Lobby title and show errors without shifting content. On phones the lobby goes below the rink. Reuse the live lobby in the pause menu, to the right when it fits and below otherwise. Ready and Challenge may run alongside CPU play without confirmation; a found match offers Join (ending CPU play) or Keep playing. Watching asks before leaving CPU play. Switching away from a live online match confirms the forfeit.
- Never use browser UI: no `confirm()`, `alert()`, `prompt()`, native `<select>` popups or other browser-styled pickers. Use the shared components in `web/game-ui.js` (dialogs, anchored dropdowns, selects).
- Dropdowns, menus and pickers overlay and drop down from their trigger. Never insert them inline so content moves.
- Icons are Tabler icons, shown as plain icons for small actions. Never use font or text symbols (arrows, ×, ✕, ▾, …) as icons. If a needed icon is missing, add it to the shared SVG icon set. Use arrows on navigation buttons where they carry meaning.
- Grids of choices show at most four per row.
- The designer and workbench pages (`demo.html`, `voice.html`, `effects.html`) are tools and are exempt for now.
- Whenever visual effects or sound effects are added or modified (e.g. in `web/ububall-presentation.js`, `shared/ubu-audio.js`, `shared/ububall-physics.js`, or `shared/ububall-match.js`), always check `web/effects.html` and `EFFECT_GROUPS` in `web/effects.js` and update the corresponding catalog descriptions (`title`, `when`, `visual`), variants, scenarios, and sound buttons so the Effects Demo stays accurate.

## Implementation hygiene

- Architecture requirement: a lean mint with zero fluff in code, UI, dependencies, tooling and documentation. Every addition must serve a current requirement; do not build speculative functionality or extension infrastructure.
- Use plain JavaScript and platform APIs by default. No framework, generic plugin system, abstraction layer, build pipeline or dependency without a concrete need that the simpler implementation cannot reasonably meet. Development tooling must also justify its cost.
- Keep the mint request path limited to required generation, validation, cryptography and persistence. Rendering and preview work belongs outside that path. Avoid repeated setup, unnecessary allocations, duplicate conversions and unbounded caches; weigh table memory/startup cost against saved work.
- Prefer one implementation of each rule. Keep modules, API surfaces, UI, logs and documentation small and purposeful; do not duplicate protocol specifications across files.
- Optimize against measured bottlenecks and representative workloads. Report CPU/latency, memory, startup and code-size tradeoffs when material. Do not claim absolute optimality or improved performance without evidence; fewer lines alone is not proof of efficiency.
- Efficiency never permits changing approved DNA laws, weakening randomness or cryptography, bypassing authorization or dropping atomic ownership guarantees. Use platform cryptography; do not implement custom cryptographic primitives.
- Keep private keys, tokens, local bindings and state out of Git, logs and examples. Use placeholders in committed configuration.
- Windows deployment: run `install.ps1` from the source checkout to copy current source into sibling `ubumint-cloudflare`, test and deploy; `-DryRun` performs validation without uploading. The installed copy in `ubumint-cloudflare` also acts as an entry point and forwards updates to the source checkout. Deployment is an explicit operator action. Never use Git pull/stash in the deployment copy. Production settings and permanent mint keys live outside Git in `%LOCALAPPDATA%\ubumint\settings.json`; preserve them and never run `-Setup` for an existing mint. `wrangler.jsonc` is the development template; generated `wrangler.deploy.jsonc` is ignored. Keep `keep_vars` enabled and do not replace saved production settings with development defaults. See docs/worker.md.
- Both test scripts default to the dot reporter. Use a detailed reporter only when diagnosing a failure.
- A fresh mint reset uses `deploy.ps1 -ResetMint` (or `install.ps1 -ResetMint` to install updates too). It backs up settings and replaces mint identity, signing keys and session secret, retaining deployment/Discord settings and allowance. This selects a fresh registry; it does not physically erase the old Durable Object. Never reset only serial counters under an existing mint identity. Retry a failed reset deployment without `-ResetMint`.
- Run repository commands inside this repository.
- Add focused verification for protocol, cryptographic, authorization and accounting boundaries when implemented; setup documentation does not need invented tests.
- Run npm test and npm run test:worker for Worker/auth/mint changes. The latter uses isolated local Cloudflare runtime storage, never a remote deployment. Public assets must use the explicit whitelist in scripts/prepare-assets.cjs; never serve the repository root. ubu-render.js is shared by the designer and site; preserve established finishes and lighting.
